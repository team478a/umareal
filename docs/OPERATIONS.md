# 開発と開催日の運用

## 現在利用できる機能

LINEまたは確認済みメールによる無料会員登録、ログイン、予備メール、LINE連携、通知設定、同意履歴、二段階認証、担当レースの確認、管理者の会員/監査一覧、有限期間権限付与API、レース・出走馬・担当者管理、CSV取込、事前評価、パドック評価、最終予想の公開・訂正・会員表示、結果確定と公開版別参考成績、ローカル料金・契約試験を利用できる。初回の管理者はローカルseedで作成し、本人が認証アプリを登録する。

## 無料登録とメール配信

LINE登録はOAuth完了後に15分有効の使い切りgrantを発行し、成人確認と版付き規約・プライバシー同意を保存して完了する。既存LINE subjectは新規会員へ再割当しない。LINE登録者は有料申込またはLINE解除の前に、予備メールと12文字以上のパスワードを確認する。

メール登録と予備メール確認は30分有効の使い切りURLを使う。`MAIL_TRANSPORT=test` は `.local/mail` にだけ出力し、本番起動を拒否する。`MAIL_TRANSPORT=resend` では管理画面または環境変数に完全なResend API key、送信元、Webhook signing secretが必要。資格情報、URL token、レスポンス本文をログへ出さない。

メール確認待ちはADMINがAAL2で`/admin/registration-followups`を確認する。登録から30分以上を初期の要確認目安とする。ローカル認証では対象メールアドレスを照合し、会員からの未着連絡など具体的な理由を入力して再送する。同じ会員への再送は5分間隔で、操作は監査へ追記される。Supabase認証では管理画面から送信せず、会員へ`/verify-email`を案内して本人のブラウザーから再送してもらう。

## 会員の利用準備

`/account`の「利用準備」で、無料登録、対象レース告知・最終予想のLINE受信、予備ログイン、有料閲覧の4状態を確認する。LINEは連携の有無だけでなく、通知設定オフとLINE側ブロックを区別して表示する。ブロック時は公式アカウントを再追加し、通知設定オフ時は画面から受信を有効にする。

未公開のレース詳細からLINE通知設定へ、有料予想のロック画面から料金確認へ移動できる。開発用申込でもプラン、料金、期間、1日利用日を最終確認してから確定する。

`/notifications`ではLINE配送の成功・失敗に関係なく、Web上で対象レース告知と閲覧権限内の予想公開履歴を確認できる。「詳細を見る」で既読を保存してレース詳細へ移動する。通知イベントと既読情報は別テーブルで管理し、公開済み予想や告知を変更しない。

`/races`では開催日を前後移動し、競馬場、対象レース告知済み、最終予想公開済み、未公開で絞り込める。公開範囲と訂正版を一覧で確認し、詳細へ移動する。一覧には予想本文、印、買い目、信頼度を返さない。

ログイン中のホームは未読件数、LINE受信状態、会員プランを表示する。未読確認、LINE設定、料金確認、公開中レースの順で、現在必要な操作を1つ案内する。上部バーの通知ベルは画面幅に関係なく未読件数を表示する。Webお知らせは登録後に発生したイベントだけを未読・履歴対象にする。

管理ダッシュボードは無料登録、本人確認、LINE準備、料金閲覧、申込確認、有料化の人数を表示する。直近30日の値は、その期間に登録した会員を母集団とする。料金閲覧と申込確認はログイン会員ごとの初回到達を記録し、再読み込みや再操作で加算しない。計測開始以前の閲覧は復元しないため、画面の計測開始日時と合わせて判断する。

開催日運用ボードはJST日付ごとに担当者、対象レース告知、全出走馬のパドック完了数、最終予想公開、通知配送、結果確定を表示する。発走30分以内は期限接近、発走後の未公開は期限超過として示す。担当未設定、出走馬未登録、未告知、パドック未完了、最終未公開、通知失敗、発走後の結果未確定を警告として数える。管理者は対象レースの評価・公開へ直接移動でき、運営担当はレース・通知・結果画面から対応する。

運用ボードは画面が表示されている間、30秒ごとに状態を再取得する。非表示タブでは通信を止め、再表示時に即時更新する。発走までの表示は端末時計で1秒ごとに進む。最後の正常取得から90秒を超えた場合、または取得に失敗した場合は鮮度警告を出す。「今すぐ更新」で手動取得でき、日付を素早く切り替えた場合は古い応答を破棄する。

開催日リハーサルは、レース準備、対象レース告知、パドック評価、最終予想公開、通知確認、結果確定の順に確認する。完了、次に確認、待機、要対応、発走後をサーバー保存データから判定する。CSV取込、予想公開、LINE通知、LINE資格情報の事前確認も同じ画面に表示する。チェック表示自体は公開・送信・結果確定を実行せず、各管理画面で既存の確認手順を行う。

`/admin/incidents`は、予想公開・CSV取込・メール・LINE通知の停止、LINE設定不足、失敗配送、初回処理が60秒を超えた配送、送信中で5分を超えた配送、24時間以内の未照合Webhookを検知する。重大、警告、案内中に分類し、30秒ごとに更新する。初動は検知範囲の確認、Web公開の確認、影響の抑制、原因解消と復旧、運用ボード・通知履歴・監査ログによる再確認の順で行う。

障害対応画面の会員向け案内文は下書きであり、自動送信しない。内容と影響範囲を確認してから既存の案内手段で使用する。緊急停止の変更は管理者が理由付きで行い、通知再送も原因解消後に理由を記録する。運営担当は検知と通知対応を行い、管理設定の変更は管理者へ依頼する。

## スマートフォンからの対象レース告知

`/admin/races`で開催日を選び、「対象レース告知」に理由を入力して公開する。告知は削除・上書きせず、再告知を新しい版として追加する。公開と同じトランザクションで無料会員向け通知eventを作る。メール・LINE通知には開催日、競馬場、レース番号、レース名、会員ページURLだけを含める。

告知後はホームの「予想対象レースのお知らせ」と通知運用を確認する。LINE通知停止中も告知とeventは保持され、再開後にワーカーが受信者を確定する。発走済み、終了、中止のレースは告知できない。

## ローカル料金・契約

`BILLING_TRANSPORT=test` でのみ開発用申込を処理する。外部決済、カード情報、実請求、返金は扱わない。`/admin/settings` で価格、創設会員販売、販売上限、支払猶予、新規購入停止を管理し、変更理由を監査する。`/admin/billing` の失敗・回復操作もローカル試験専用で理由を必須にする。

支払履歴と請求イベントを修正・削除しない。訂正が必要な場合は新しいイベントまたは支払試行を追加する。解約予約後も契約期間終了までは閲覧権限を維持する。ローカル決済に定期更新ジョブはないため本番運用へ使わない。

## ローカル環境

.env、.localはGit管理外。パスワード再設定メールと初期担当者パスワードも.local内に限定。画面へ実際の個人情報を入力しない。データの削除・DBリセットは自動実行しない。

起動方法と検証コマンドはREADME参照。Dockerが使える場合はComposeを優先。この環境で利用した補助PostgreSQLはループバック専用で、stopコマンドはデータを保持する。

## 認証で問題がある場合

- 401: セッション期限切れ・失効を確認して再ログイン。
- MFA_REQUIRED: /securityで認証アプリのコードを入力。
- MFA_REPLAY: 同じ30秒のコードを再利用せず次のコードを待つ。
- ORIGIN_REJECTED: APP_BASE_URLとブラウザーのscheme/host/portを一致させる。
- 429: 1分待って再操作。本番ではプロセス間の制限共有が必要。
- 500/503: requestIdで調査。ログにはエラー種別のみ記録し、秘密値を追加しない。

## 運用・連携設定

`/admin/settings` はADMIN+AAL2だけが変更でき、OPERATORは状態確認だけ行える。すべての変更に理由が必要で、設定値、実行者、時刻を監査ログへ保存する。Channel secretとChannel access tokenは保存後に取り出せないため、変更時は新しい値を再入力する。

## ローカル通知ワーカー

Phase 3Bは外部LINEへ接続せずtest transportで配送状態を検証する。管理画面でLINE通知を有効にしてから、ビルド済みワーカーを1回だけ処理する場合は `pnpm --filter @keiba/worker run:once`、5秒間隔で継続処理する場合は `pnpm --filter @keiba/worker start` を使う。ワーカーは件数と状態だけを標準出力へ記録し、LINE subject、トークン、秘密値、本文は出力しない。

`NODE_ENV=production` ではtest transportの起動を拒否する。`/admin/notifications` で失敗理由と履歴を確認し、原因を解消した後に理由を入力して再送する。全体停止中のキューは変更されず、設定を再開してからワーカーが処理する。

## LINE接続準備の確認

`/admin/settings` はMessaging APIとLINE Loginを分けて準備状態を表示する。暗号化データの検証は、保存値を現在の `ENCRYPTION_KEY` で復号できたことだけを示し、秘密値はAPIレスポンスやログへ出さない。「外部疎通は未実施」が表示されている間はLINE Developers側との接続確認を完了扱いにしない。

本番接続前にHTTPSの `APP_BASE_URL`、LINE Developers側のWebhook URL、送信元チャネル、アクセストークン権限を照合する。ライブ疎通と実会員への送信は対象と時間を決めた別作業で行う。

## Messaging API transportとWebhook

`NOTIFICATION_TRANSPORT=line` でワーカーは管理画面に暗号化保存したChannel access tokenを読み、固定のLINE push APIへ送信する。資格情報や送信先を標準出力へ出さない。`test` はローカル検証専用である。`LAUNCH_MODE=FREE_REGISTRATION` の本番ではLINE transportの`disabled`を必須にし、workerはLINE配送を展開せず、予約公開とメール配送を処理する。`FULL` の本番はLINE transportの`line`を必須にする。ライブ切替前に通知キューと対象会員を確認し、意図しない一斉送信がない時間帯に行う。

メール公開通知は `MAIL_TRANSPORT=resend` で有効にする。初回起動はAPIとworkerに同じ `RESEND_API_KEY` と `MAIL_FROM`、APIに`RESEND_WEBHOOK_SECRET`を設定し、初回管理者の準備後は `/admin/settings` から3項目を暗号化保存できる。管理設定が一項目でもあれば環境変数と混在させず、APIの認証メールとworkerの公開通知が同じ設定を使用する。workerは確認済みメール、本人のメール全体・カテゴリ設定、配信拒否状態、有料公開の権限を送信直前にも確認する。管理画面の「メール通知」は緊急停止であり、停止中に作られた新規eventは再開後に処理される。初回有効化前に `/admin/notifications?channel=EMAIL` で対象件数を確認する。既存eventはPhase 6P移行時に展開済みとなり、過去分は送信されない。

ResendでWebhook URLを`https://<公開ドメイン>/api/v1/webhooks/resend`に設定し、`email.bounced`、`email.complained`、`email.suppressed`、`email.failed`、`email.delivery_delayed`を購読する。署名検証後、前3種は照合した会員の公開通知メールを自動停止する。`email.failed`と遅延は送信者設定・上限・一時障害の可能性があるため会員を停止せず、`/admin/incidents`と`/admin/notifications`で確認する。Webhookは重複し得るため`svix-id`で冪等化し、配信順序に依存した自動解除は行わない。本人が受信可能な状態にしたことを確認後、AAL2管理者が理由付きで停止を解除する。解除時も本人の通知設定は無効のままとし、本人が明示的に再開する。

Webhook URLは `{API公開URL}/api/v1/webhooks/line`。LINE Developers側でWebhook再送を有効にできるが、アプリは `webhookEventId` で重複を拒否する。管理画面の通知運用で最終受信、24時間件数、未照合、通知不可アカウントを確認する。初回送信から24時間を越えた配送は同じリトライキーの保証期間外になるため再送しない。

予想公開またはCSV取込を停止すると、新しい確認処理と確定処理の両方を拒否する。停止前に作成したプレビューも確定できない。復旧時は停止理由と外部状況を確認してから再開し、公開済み予想や取込済みデータは変更しない。

LINE通知を有効にしても現区間では送信しない。次区間のワーカーは送信直前にこの設定と会員の通知設定・閲覧権限を再確認する。`ENCRYPTION_KEY` を変更すると保存済み資格情報とMFA秘密を読めなくなるため、鍵移行手順なしに変更しない。

## 開催日手順

1. 開催日・対象レース・出走馬・担当者を登録。CSV差分と発走時刻を確認。
2. 専門家が担当レースを開き、事前点数・順位・印を入力。保存状態が「保存済み」になることを確認。
3. 1頭ずつパドック5項目・総合変化・短評を入力。「判断不能」は入力済みとして扱う。通信切断中は「未送信」となり、復帰後の再同期を確認。
4. 競合表示時は端末とサーバーの値を比較し、採用する内容を明示する。全頭の入力状況で未入力・未送信を確認。
5. 全頭パドック評価後、最終印・信頼度・勝負判断・総評・参考買い目を入力。公開前画面で馬番、公開範囲、未入力警告、点数・総額、締切を確認して確定する。
6. 訂正は新しい版を作成し旧版を残す。発走後は訂正版を作らない。
7. LINE障害時もWeb公開を維持し、通知履歴で再試行状況を確認。
8. レース終了後、取消/除外/中止/払戻を確認して結果を確定。全成績を再計算。

結果確定では全馬の状態と着順を確認し、的中または返還となる組合せだけを100円あたりの金額で入力する。取消・除外を含む公開買い目のREFUNDが不足すると確定できない。公式訂正時は下書きを更新し、新しい結果版として確定する。過去の結果版と成績は変更しない。

第1〜8項のローカル運用基盤は実装済みです。[CSV取込手順](CSV_IMPORT.md)を参照してください。予想訂正は開発既定値で管理者が担当レース画面から公開します。結果のCSV取込と正式データ提供元、LINEのライブ疎通、外部決済は未実施のため、本番の開催日運用にはまだ使用しないでください。

## 無料会員向け配信

管理者または運営担当は `/admin/free-reports` を開く。登録特典には公開済みの動画HTTPS URL、タイトル、説明、変更理由を設定する。レース速報は開催日とレースを選び、評価UP馬・DOWN馬を各1頭、各理由を入力する。本人音声は「マイクで録音」で録音するか、端末内の音声ファイルを選ぶ。録音終了後の試聴を確認し、保存理由を入力して下書きを保存する。外部配信済み音声は詳細欄からHTTPS URLを入力できる。発走前速報の配信内容を開き、次版、対象会員、LINE・メール別件数、本文を確認してから公開する。

公開後は版を更新・削除しない。訂正が必要な場合は下書きを修正し、新しい発走前版を公開する。公開により無料会員向けWebお知らせとLINE配送eventが作成される。LINE本文には馬番・馬名・評価理由を出さず、ログイン後のレース詳細で本文を確認させる。

レース後は確定結果を先に登録し、同じ画面で簡易検証と理由を保存する。レース後検証の配信内容を開き、対象会員と通知本文を確認してから公開する。発走前版、発走時刻の経過、確定結果、検証コメントが揃うまで確認・公開できない。音声は最大8MBで、録音は5分で自動終了する。登録特典動画のアップロード機能はないため、事前に管理対象のHTTPS配信先へ配置する。

## 配信予約とアラート

`/admin/publication-schedules` で開催日とレースを選び、対象レース告知または無料パドック速報、公開日時、理由を入力する。どちらも「配信内容を確認」を開き、対象会員、LINE・メール別件数、本文、予定時刻を確認してから予約する。人数はその時点の参考値で、実行時に会員の通知設定とチャネル停止状態を再判定する。無料速報は先に `/admin/free-reports` で下書きを保存する。予約後に下書きを変更すると、旧内容を自動公開せず予約が失敗状態になる。修正内容を確認して新しい予約を作成する。

予約を止める場合は予約行へ取消理由を入力する。公開済みまたは実行済みの予約は取り消せない。ワーカーは5秒間隔で期限到来を確認し、公開版と通知eventを同じ処理で作成する。

画面上部のアラートには、発走30分以内の未告知、下書き作成済みで未公開・未予約の無料速報、実行時刻から1分以上遅れている予約、予約実行失敗、通知配送失敗を表示する。通知失敗の受信者と再送理由は `/admin/notifications` で確認・入力する。

公開後は各レースの「配信結果」で、対象レース告知・無料パドック速報・レース後検証の公開版ごとにWeb掲載日時とLINE・メールの送信済み、待機、失敗、対象外件数を確認する。「受信者別の詳細」を開くと、そのレースの配送だけを通知運用画面へ絞り込める。失敗がある場合は配送試行を確認し、原因を解消してから理由付きで再試行する。過去版の結果も削除せず、訂正版を新しい版として追記した経緯を残す。

## ローカルバックアップ・復元確認

開発用PostgreSQLが起動している状態で、リポジトリ直下から `pnpm db:backup:verify` を実行する。処理中は元DBを安全停止するため、Web/APIを操作しない。スクリプトは物理コピー、SHA-256、隔離ポート55433での起動、主要件数・マイグレーション・不変化トリガーの照合、一時データ削除、元DB再起動を行う。

結果は管理者が `/admin/backups` で確認できる。バックアップ本体と状態ファイルは `.local/backups` にあり、Git管理外である。ローカル成果物は未暗号化なので外部へ移動しない。失敗時は `.local/postgres/server.log` と、残っている場合だけ `.local/restore-verification/<backupId>/postgres.log` を端末上で確認する。ログや状態ファイルへDB URL、パスワード、トークンを転記しない。

本番ではこの手順を使わず、選定したDBサービスの暗号化バックアップ、別拠点保管、保持期間、復元テスト、RPO/RTO、監視通知を定義する。

## 退会と履歴保持

無料会員はマイページの「退会条件を確認」から手続きを行う。月額契約または1日利用の期間中は退会できない。月額は先に解約予約し、表示された利用終了後に再度手続きする。

完了時に全セッション、LINE連携、通知設定、現在・将来の閲覧権限が停止する。ログインし直すことはできない。管理者は `/admin/account-closures` で停止日時と保持方針を確認し、監査ログの `ACCOUNT_CLOSED` と照合する。退会記録、公開・評価、支払・契約、同意、監査履歴は削除しない。

本人から個人情報の削除・開示を求められた場合は、この開発機能だけで完了扱いにしない。正式な保持期間、本人確認、法定保存対象、匿名化手順を確定してから別の運用手順で扱う。

## 本番前の必要事項

実Supabaseのメール確認・更新・MFA復旧・ログアウト試験、ローカル認証の起動拒否確認、DB所有者とアプリ権限の分離、監査保持期間、暗号化バックアップと復元試験、負荷試験、正式文書の同意、データ利用許諾の確定。

管理者はAAL2完了後に `/admin/readiness` を開き、「要対応」を解消し、「人による確認」を公開責任者と確認する。画面は環境変数や暗号化資格情報の有無だけを判定し、値を表示しない。外部疎通、契約・法務判断、監視の発報、暗号化バックアップの復元は各サービス上で別途確認する。この画面の状態だけで本番公開を決定しない。

## Stripe Checkout

`LAUNCH_MODE=FREE_REGISTRATION` では `BILLING_TRANSPORT=disabled` とし、会員向け購入画面と購入APIを停止する。`FULL`へ進むときに `BILLING_TRANSPORT=stripe` を配備時の安全スイッチとして設定し、Secret key、Webhook secret、テスト／本番モード、創設・通常・1日利用のPrice IDは `/admin/settings` で管理する。管理画面の秘密値は暗号化され、保存後は再表示されない。管理画面未設定時だけ同名の環境変数を互換用フォールバックとして使う。Webhook URLは `{API公開URL}/api/v1/webhooks/stripe`。Checkoutの完了画面だけでは権限を付けず、`checkout.session.completed` の署名、live/testモード、JPY金額、内部申込ID、会員ID、プランを照合してから反映する。

新規会員募集を一時停止する場合は、ADMINがAAL2で `/admin/settings` を開き、「新規会員登録」を無効化し、会員向け案内と監査用の変更理由を入力する。保存後にシークレットブラウザーで `/register` の案内と、既存会員の `/login` が利用できることを確認する。再開時はスイッチを有効化し、停止案内を空にして理由付きで保存する。停止中もメール確認とパスワード再設定を止めない。

Webhookには `checkout.session.completed`、`invoice.paid`、`invoice.payment_failed`、`customer.subscription.updated`、`customer.subscription.deleted` を登録する。更新成功はInvoiceの請求期間へ権限を更新する。失敗は管理設定の猶予期限を反映し、期限後は時刻ベースの権限判定で有料本文を返さない。契約終了は即時失効する。外部決済モードでは管理画面のローカル失敗・回復操作を拒否する。

管理者は `/admin/billing` の外部決済申込とWebhook受信結果を確認する。`REJECTED` は金額や申込の不一致、`IGNORED` は対象外イベント、`PROCESSED` は反映済みを示す。Webhook secret、カード情報、イベント本文は保存・表示しない。ライブ接続前にStripe CLIまたはテスト環境で正常完了、重複配信、不正署名、金額不一致を確認する。

環境変数から管理画面へ移行するときは、Secret key、Webhook secret、3つのPrice IDを同じ保存操作で入力する。一部だけ保存するとDB設定が優先され、外部決済は設定不足として停止する。本番モードはライブSecret keyと一致させ、本番配備では環境変数 `STRIPE_LIVE_MODE=true` も必要とする。
